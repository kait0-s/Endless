# Endless マップ・部屋生成システム要件定義書

版: Draft 0.4
更新日: 2026-09-16  
対象: マップ担当・実装担当

## 1. 文書の目的

本書は、Unreal Engine 5.6で制作する三人称アクションゲーム `Endless` の完成版における、マップ、部屋生成、部屋接続、ドア管理、読み込み、部屋状態管理の要件を定める。

固定2部屋テストなどの開発手順は本書に含めず、別途実装計画書で管理する。武器内部処理、ダメージ計算、HUD、敵AI内部ロジックなどは本書の対象外とし、マップシステムとの接続条件だけを扱う。

## 2. ゲーム概要

| 項目 | 要件 |
|---|---|
| エンジン | Unreal Engine 5.6 |
| 対象環境 | Windows PCを中心とし、将来の拡張を妨げない構成とする |
| ジャンル | 1人用三人称アクション |
| 舞台 | 学校・オフィス系の屋内施設 |
| 主な行動 | 銃撃、近接戦闘、ステルス、探索 |
| ゲーム方式 | プレイヤーが死亡するまで続くエンドレス方式 |
| 進行形式 | 部屋を順番に接続する一本道。直前の1部屋のみ戻れる |
| 死亡時 | ラン中の武器、能力、部屋、敵、物資、進行度、難易度をリセット |

## 3. 開始地点

開始地点は通常部屋とは別規格の専用廊下とする。

| 項目 | 要件 |
|---|---|
| 形状 | 直線廊下 |
| 寸法 | 幅4m、長さ8m |
| ドア | プレイヤー正面奥に進行用ドアを1枚配置 |
| 配置物 | 台の上に初期武器を1つ配置 |
| 敵・罠 | 配置しない |
| 最初の部屋 | 通常戦闘カテゴリに固定 |

初期武器を取得せずに最初のドアを操作した場合は警告する。プレイヤーが警告を確認した場合は、武器を取得せずに進むことも許可する。死亡後は開始廊下から完全にやり直す。

マップ側は初期武器配置ポイントと未取得警告の要求を提供する。武器の種類、取得処理、装備処理はゲーム側が管理する。

## 4. 基本進行フロー

1. プレイヤーが現在部屋へ入る。
2. 進行用ドアごとに次室候補を決定する。
3. 候補ごとのカテゴリ、レイアウト、家具セット、敵配置、敵能力、物資、乱数シードを保持する。
4. プレイヤーがドアから600cm以内へ近づくと、そのドアの候補部屋を生成する。
5. プレイヤーがドアから50cm以内に入り、ドアへ向いたときに操作可能とする。
6. 進行用ドアを1枚開けると進行先が確定し、未選択ドアを永久ロックする。
7. 接続済みの次室へ入り、同じ処理を繰り返す。

進行用ドアには、敵の全滅やイベント完了などのゲーム上の解放条件を設けない。プレイヤーは戦闘、ステルス、イベントを完了せずに次室へ進める。

## 5. 部屋構成

### 5.1 ドア数

通常部屋のドア数は、戻り用を含めて合計2～4枚とする。

- 戻り用ドア: 1枚
- 進行用ドア: 1～3枚
- 1つの壁面に配置できるドア: 最大1枚
- 開始廊下はこの枚数規格に含めない

### 5.2 初期レイアウト

| レイアウト | 寸法 | 通常天井高 | 特徴 |
|---|---:|---:|---|
| 教室 | 20m × 20m | 4.5m | 机や棚を利用した近距離・中距離空間 |
| オープンオフィス | 20m × 30m | 4.5m | デスクやパーティションによる複数経路 |
| 廊下・ロッカー | 12m × 30m | 4.5m | 長い射線とロッカー、曲がり角 |
| エントランスホール | 30m × 30m | 8.0m | 階段、吹き抜け、立体的な経路 |
| 実験室・サーバー室 | 20m × 20m | 4.5m | 機材列、端末、罠、特殊イベント |

壁厚は0.2mとする。初期5レイアウトを基準とし、同じ規格で後からレイアウトを追加できるようにする。

1つのレイアウトは複数カテゴリで使用可能とする。カテゴリに応じて敵、イベント、物資、演出を変更する。

### 5.3 ドア位置

各壁面に以下のドア位置規格を設ける。

- 中央
- 左端寄り: 室内から壁面外側を見たとき、左側の角からドア中心まで4m
- 右端寄り: 室内から壁面外側を見たとき、右側の角からドア中心まで4m

中央・端寄りの種類が異なるSocket同士も接続可能とする。接続時はSocketの位置、向き、床高を一致させる。部屋は90度単位で回転可能とする。

## 6. 部屋接続

- 次室は同じ空間内へ直接接続する。
- ロード画面や別空間へのワープは使用しない。
- 基本的に接続廊下を挟まない。
- 接続面に段差、隙間、壁の重なりを発生させない。
- 未使用のドア位置は壁として閉じる。
- 進行ルートは枝分かれさせない。

同じレイアウトは連続出現させない。同じカテゴリは最大2部屋まで連続可能とし、2部屋連続した場合は次回候補からそのカテゴリを除外する。

## 7. 部屋カテゴリと抽選

| カテゴリ | 基本的な特徴 |
|---|---|
| 通常戦闘 | 標準的な敵構成と遮蔽物を使用 |
| ステルス | 視線回避、隠れ場所、警戒状態を重視 |
| 高難度・強敵 | 強敵、エリート、厳しい敵配置を使用 |
| 罠・特殊イベント | 端末、罠、危険床、追加敵などを使用 |

開始廊下の先は通常戦闘に固定する。2部屋目以降の4カテゴリは基本的に各25％とする。連続制限によってカテゴリを除外した場合は、有効なカテゴリ間で確率を均等に再配分する。

同じ現在部屋にある複数の進行用ドアへ、同じカテゴリが割り当てられることを許可する。

## 8. ドアのカテゴリ表現

カテゴリ名は入室前後とも画面へ表示しない。ドアの以下の外観だけで次室の傾向を曖昧に示す。

- 材質
- 色
- 傷
- 汚れ

同じカテゴリにも複数の外観パターンを用意する。外観とカテゴリを完全な一対一対応にはせず、プレイヤーが経験から傾向を推測できる程度にする。

## 9. ドア仕様

| 項目 | 要件 |
|---|---|
| Blueprint | 専用の `BP_RoomDoor` を新設する |
| 寸法 | 幅1.0m、高さ2.2m |
| 形状 | 通常サイズの1枚開き戸 |
| 操作距離 | キャラクターから50cm以内 |
| 操作方向 | プレイヤーがドアへ向いている場合のみ |
| 開閉方向 | 操作した側から見て奥側へ開く両方向スイング式 |
| 自動閉鎖 | 行わない |
| 手動操作 | 接続後は両側から開閉可能 |

ドアの回転範囲にプレイヤーがいる場合は、安全側へ押し出す。扉の回転範囲には敵、大型家具、小物、物資、罠を配置しない。

開放中もドア境界を越える弾丸、近接判定、ダメージ判定を双方とも無効化する。攻撃無効境界は画面上へ表示しない。敵はドア境界を越えて別室へ移動しない。

## 10. 配置ルール

### 10.1 安全範囲と経路

- 各ドアから室内側2mを安全範囲とする。
- 安全範囲に敵、大型家具、小物、物資、罠を配置しない。
- 各部屋に最低2本の主要移動経路を確保する。
- 完全な一本道や長い行き止まりを避ける。
- 三人称カメラとキャラクターが継続的に干渉しない幅を確保する。

### 10.2 家具

各レイアウトに、検証済みの手作り家具配置セットを3種類用意する。大型家具と主要遮蔽物はセット単位で抽選し、個別の完全ランダム配置は行わない。

### 10.3 小物

小物は指定された候補エリア内へランダム配置する。ただし、以下の条件を満たすこと。

- 主要移動経路を塞がない
- ドア前2mへ入らない
- 扉の回転範囲へ入らない
- 家具、小物、壁と重ならない
- NavMesh上の主要経路を失わせない

配置に失敗した場合は再試行し、配置可能位置がなければその小物を生成しない。

### 10.4 敵と物資

- 敵配置は検証済みのEnemySpawnPointから抽選する。
- 物資の種類と位置は検証済みのLootSpawnPointまたは許可領域から抽選する。
- 物資の種類と位置は次室候補を決める時点で確定する。
- 敵は部屋生成時に準備するが、プレイヤーが部屋へ入るまでAIを停止する。
- プレイヤーがドア境界を越えた時点で敵AIを起動する。
- 回復と弾薬は部屋内配置と敵ドロップの両方から入手可能とする。

## 11. 攻略と報酬

進行用ドアは常に利用可能とし、部屋攻略を必須にしない。プレイヤーは敵やイベントを無視して次室へ進める。

敵の撃破、ステルス成功、強敵撃破、イベント完了には、物資とスコアの両方を報酬として設定する。詳細な報酬量とスコア計算はゲーム側の仕様とする。

敵を残して進んだ場合、敵の生存、体力、警戒、撃破状態を前室に保持する。前室へ戻った場合は保持状態から再開する。

## 12. 候補確定と難易度

現在部屋への入室時に、各進行用ドアについて以下を確定する。

- カテゴリ
- レイアウト
- 使用する入口Socketと回転
- 家具配置セット
- 敵の種類、数、配置、能力
- イベント構成
- 物資の種類と配置
- 小物配置用乱数シード
- 同カテゴリの予備候補

開始廊下では経過時間を計測しない。最初のドアを通過した瞬間をラン開始とする。通常部屋へ入るたびに進行部屋数を加算する。

次室候補の難易度は、候補を決める時点の進行部屋数と経過時間から算出する。候補確定後は、生成や入室まで時間が経過しても再計算しない。

難易度上昇に上限は設けず、死亡まで継続する。具体的な数式、係数、敵能力への配分は調整データとして別途定める。

## 13. 読み込みと保持

同時に実体化する部屋は以下の最大3部屋とする。

1. 直前部屋
2. 現在部屋
3. 生成中または生成済みの候補部屋1つ

複数ドアの候補データは保持できるが、同時に実体化する候補部屋は1つに制限する。

プレイヤーが前室へ戻った場合、開いていない候補部屋の実体をすべてアンロードする。候補データは保持し、現在部屋へ再入室しても再抽選しない。再接近時は同じ候補を再生成する。

進行用ドアを開けた瞬間に進行先を確定し、未選択ドアを永久ロックする。同時に、それまでの前室を削除する。したがって、進行用ドアを開けた時点から古い前室には戻れない。

## 14. 重なりと読み込み失敗

候補部屋が現在部屋または直前部屋と重なる場合は、カテゴリを維持したまま、入室時に用意した同カテゴリの予備候補へ切り替える。カテゴリはドア外観との整合性を保つため変更しない。

部屋の読み込みに失敗した場合は再試行する。再試行後も失敗した場合は、配置保証済みの同カテゴリ予備部屋を使用する。配置と読み込みが完了するまでドアを開放せず、操作表示を「待機中」へ変更する。

再試行回数とタイムアウト時間は実測後に調整データとして定める。

## 15. 状態管理

前室へ戻る可能性がある間は、以下の状態を保持する。

| 対象 | 保持内容 |
|---|---|
| 敵 | 生存、撃破、残り体力、警戒状態、AI起動状態 |
| 物資 | 配置、取得済み状態 |
| オブジェクト | 開封、破壊、端末操作、罠の作動状態 |
| ドア | 候補、接続先、開閉、施錠、進行確定状態 |
| 部屋 | カテゴリ、レイアウト、配置セット、乱数シード、攻略状態 |

部屋を削除した場合は、その部屋に属する敵、物資、オブジェクト、候補実体を破棄する。

## 16. ラン終了と中断

- 死亡時はランを終了し、最終スコアをゲーム側へ渡して記録する。
- ラン中の部屋、敵、物資、武器、能力、時間、進行数、難易度をリセットする。
- 再開始時は開始廊下から始める。
- 一時停止からは同じ状態で再開できる。
- 一時停止中は難易度用の経過時間を停止する。
- アプリケーション終了またはタイトルへ戻った場合、進行中のランは保存しない。
- 次回開始時は新しいランとして開始する。

スコアの保存形式、履歴、ランキングはゲーム側の責任範囲とする。

## 17. 性能要件

- ドア操作から開放まで0.5秒以内を性能目標とする。
- 0.5秒は現段階では強制的な合格条件ではない。
- 重い同期読み込みをドア操作時に開始しない。
- 候補決定、先読み、接近時生成、ドア開放を分離する。
- 目標FPSは現段階では指定せず、計測値を記録する。
- PIE、Standalone、Cooked Buildを区別して計測する。
- FPS、Game時間、Draw時間、GPU時間、メモリ、ドア応答時間を記録する。

## 18. 暫定受入基準

以下は完成版へ向けた暫定的な受入基準とし、基準PC決定後に数値を再確認する。

- 全5レイアウトを任意の対応Socketで接続しても、目立つ段差、隙間、壁の重なりがない。
- 90度回転後も接続と移動に問題がない。
- ドア前2mと扉回転範囲に禁止対象が生成されない。
- 主要経路が小物によって塞がれない。
- 全EnemySpawnPointから主要経路へNavMeshで到達できる。
- 候補切り替え時に不要な部屋実体が残らない。
- 前室へ戻っても敵、物資、オブジェクト、ドア状態が変化しない。
- 進行ドアを開けると未選択ドアが永久ロックされ、古い前室が削除される。
- 同時に実体化する部屋が最大3部屋を超えない。
- 100部屋以上連続して進行しても、接続不能、参照切れ、進行不能、継続的なメモリ増加が発生しない。
- 読み込み失敗時に予備部屋へ切り替わり、ランが進行不能にならない。

## 19. 調整値と未確定事項

以下は要件の骨格を変更せず、デモとプレイテストで調整する。

- 難易度計算式、係数、敵能力への反映量
- 敵数、敵種類、物資、ドロップ率の上下限
- 家具配置セットと小物候補エリアの具体的内容
- カテゴリごとのドア外観パターン
- スコアと報酬量
- 読み込み再試行回数とタイムアウト時間
- 配置保証済み予備部屋の具体的な構成
- 基準PCと目標FPS
- ドア押し出し処理の速度と安全距離

## 20. 別資料で定める事項

以下は本要件定義書ではなく、技術設計書または実装計画書で定める。

- C++とBlueprintの役割分担
- 部屋データ構造、列挙型、構造体、Data Asset
- Level StreamingまたはLevel Instanceの具体的な採用方式
- NavMeshの生成方式
- クラス名、Blueprint名、フォルダ構成
- 固定2部屋テストの工程
- 実装順序、担当、スケジュール
- デバッグ表示、ログ、計測方法
